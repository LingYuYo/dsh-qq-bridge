# 接通 QQ：最后一公里

装好插件和桥接之后，还差这几步才能真的收发消息。按顺序做。

前置：`@local/dsh-qq-guard` 插件已装进 profile，`qq-chat` preset 已生效；`qq-bridge/` 已就位，离线自测全绿。

## 第 1 步：填白名单

复制 `config.example.json` 为 `config.json`，把你的 QQ 号填进 `allow.private`：

```json
"allow": {
  "private": [ 你的QQ号 ],
  "groups": [],
  "deny": { "private": [], "groups": [] },
  "allowAllWhenEmpty": false
}
```

不填的话桥接是 fail-closed（谁都不回，这是刻意的默认值）。

## 第 2 步：启动 NapCat（要扫码）

```bat
cd /d <NapCat 安装目录>
napcat.bat
```

> - 首次要扫码登录（用 **你的 QQ** 的手机端扫）。
> - 想免扫码快速登录：把 `napcat.quick.bat` 里的 `10086` 改成实际的 QQ 号，
>   或直接在插件设置页填「快速登录 QQ 号」。
> - NapCat 会用 `C:\Program Files\Tencent\QQNT` 里的真 QQ 注入运行，
>   和你日常开着的 QQ 是两套进程，互不干扰。
> - 启动后会有个 WebUI（默认 `http://127.0.0.1:6099`，token 在 NapCat 安装目录的
>   `.../napcat/config/webui.json`），可以在那儿核对 OneBot 的 WS 服务端配置。

## 第 3 步：启动桥接

```bash
cd <你放本仓库的位置>/qq-bridge
node start.mjs
```

看到这些就算成功：
```
DSH 鉴权通过 ✓
[bridge] NapCat WebSocket 已连接
[bridge] 已登录 QQ：<你的号>（…）
[bridge] QQ 账号在线（WS get_status 确认）   ← 纯 WS 探测，不需要 NapCat HTTP API
桥接已启动，等待 QQ 消息。
```
（若只有「已连接」没有「QQ 账号在线」，说明 get_status 没探到 —— UI 会显示
「已连接（账号状态未确认）」，不影响收发，只是账号状态未经确认。）

也可以在插件设置页里点「启动桥接」，让 DSH 托管它（崩溃会自动重启，有上限）。

## 第 4 步：用你的 QQ 私聊机器人号

发一句"你好"。桥接日志应出现：
```
新会话 u:<你的QQ号> -> session-xxxx
agent 回复 (u:<你的QQ号>) NN 字
```

回复会发回你的 QQ。

## 出问题看这里

| 现象 | 检查 |
| --- | --- |
| `DSH 鉴权失败` | DSH 是否在运行、端口探测失败且兜底 baseUrl 不可达（或用 `DSH_BASE_URL` 显式指定） |
| 日志没有"NapCat 已连接" | NapCat 没启动，或 WS 端口不是 3001，或 token 不匹配 |
| QQ 发消息毫无反应 | 先看日志有没有 `白名单外，忽略`（那就是第 1 步没填）；再看 `处理 ... 失败` |
| 回复内容奇怪/被拦 | 日志会写命中哪条审计规则，这是有意的 |

## 可复现的安全验证

想自己验证门禁真的拦得住，不能靠诱导模型 —— 模型会基于人设直接拒绝，连 tool/call
都不产生，那种「通过」证明不了 guard。要用**绕过模型**的方式取证：

1. 临时写一个诊断探针插件，暴露一个 HTTP 端点，在指定 agent 作用域里直接调
   `ctx.tools.execute()`；
2. 建一个 `qq-chat` 会话，确认探针已装载后执行：

```bash
curl "http://127.0.0.1:<DSH实际端口>/<你的探针路由>?sessionId=<会话id>&tool=ops_bash&command=echo%20X"
#    端口用探测到的实际值（见 src/dsh.mjs discoverDshBaseUrl），不要写死。
#    期望：isError=true，拒绝理由含"不在 QQ 会话白名单内"。
```

3. **验证完立刻卸载探针** —— 它本身会开一个能执行 shell 的 HTTP 端点，长期挂着等于开后门。

本仓库不分发这个探针，原因就是第 3 条。
